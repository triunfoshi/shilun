# 石论交易决策引擎与 Trading 工作空间 PRD

> 版本：v0.8  
> 编写日期：2026-07-11  
> 状态：Job 12I 已执行并暂停；生产事实桥已接通，等待真实交易窗口积累样本  
> 目标：建立独立于研究模块的 Trading 工作空间和可解释交易决策引擎，把实时事实持续转换为剧本、动作、原因和证据，并完整记录决策为何变化。
> 上线约束：首版不训练时序模型或分类模型，不依赖大样本预测；优先使用可审计、可回放、可快速校正的确定性规则。

---

## 1. 背景与问题

石论当前已有候选池盘中监控、持仓台账、MA5 日检和部分分时共振能力，但真正缺少的不是另一个策略，而是统一的**交易决策引擎（Decision Engine）**：

1. 盘中监控主要服务候选池，没有默认加载全部活动持仓。
2. 持仓日检以日线收盘为主，无法充分处理高低开、分时承接、假跌破和盘中收回。
3. 大盘只读取单一缓存权限，未分别展示上证指数和创业板指数的实时状态。
4. 个股所属板块只提供静态状态，尚未成为持仓策略的实时输入。
5. MA5 跌破后容易单向进入减仓/退出，缺少等待确认、快速收回、倒 T、策略迁移等预案。
6. 动作数量被固定比例表达，未根据有效止损、持仓数量和最大允许亏损金额动态计算。
7. 研究排名策略与交易执行策略并存，职责边界不清晰。

本 PRD 不建设自动下单。系统只计算预案、建议数量和操作区间，最终操作由用户确认并在券商端执行。MA5 v0.2 仅作为首个 Playbook 和验收样例，不再作为系统中心。

## 2. 产品定位

### 2.1 新增一级 Trading 工作空间

在当前“研究”主流程之外新增一级大 TAB：**交易**。

```text
研究
├── 数据同步
├── 大盘研究
├── 板块研究
└── 单票事实分析

交易（Trading）
├── 交易驾驶舱（默认首页）
├── 持仓台账
├── 历史交易
├── 风险设置
└── 回测
```

### 2.2 产品核心：交易决策引擎

交易驾驶舱是 Trading 的默认首页，默认监控全部活动持仓，也可以切换到观察池。页面只优先回答三个问题：

1. 现在发生了什么？
2. 为什么形成这个判断？
3. 现在应该怎么做？

页面阅读顺序固定为：

```text
Action → Reason → Scenario → Evidence → Market → Raw Data
```

指标只是证据，不直接占据第一屏。每只持仓绑定一个主 Playbook；大盘、板块和账户风险作为独立上下文与约束，不反向篡改行情事实。

```text
持仓事实 + 主 Playbook + 实时个股 + 双指数 + 个股板块
                         ↓
                 候选 Scenario List
                         ↓
              Decision Engine 编排与切换
                         ↓
                风险预算与权限约束
                         ↓
        Action + Reason + Evidence + 切换条件
                         ↓
                 Decision Timeline
```

### 2.3 明确不做

- 不接券商自动下单。
- 不使用 K 线推断“财务基本面良好”。页面统一表述为“技术结构未恶化”。
- 不建设多个 Playbook 投票；每笔持仓只绑定一个主 Playbook。
- 不允许 Playbook 失效后自动降低底线或无确认迁移到更长周期 Playbook。
- 不把固定的 20%、50% 或全部卖出写进通用动作引擎。
- 不训练或上线时序预测模型、分类模型和未经校准的概率模型。
- 不展示“上涨概率”“发生概率”或精确到分钟的操作预测。
- 不让单一指标直接生成买卖动作。

### 4.3 Playbook 协议 `PlaybookSpec`

Playbook 是完整的交易方法，例如 MA5 趋势、箱体震荡、弱转强；Scenario 是 Playbook 针对当前盘中路径生成的动态剧本。每个 Playbook 必须声明：

- 所需行情周期和指标。
- 开盘前冻结的关键位。
- 盘中动态指标。
- 剧本生成函数。
- 剧本优先级。
- 软破位和硬止损确认方式。
- 允许的持仓手法。
- 策略迁移条件。

周一版接口：

```python
class PlaybookSpec(Protocol):
    playbook_id: str
    version: str

    def build_watch_plan(self, holding, daily_facts, context) -> dict: ...
    def build_scenarios(self, watch_plan, realtime_facts) -> list[dict]: ...
    def evaluate_rules(self, scenarios, previous_state) -> dict: ...
```

```json
    }
  ],
  "action": {
    "type": "adjust_position",
    "target_quantity": 0,
    "change_quantity": -100,

```

剧本状态：

| 状态 | 中文 | 行为 |
|---|---|---|
| `far` | 未接近 | 不占据当前动作 |
| `approaching` | 接近触发 | 提示还差哪些条件 |
| `waiting_confirmation` | 等待确认 | 已满足第一阶段条件 |
| `triggered` | 已经触发 | 可以成为当前动作 |
| `invalidated` | 已经失效 | 不再参与当日决策 |
| `suppressed` | 被覆盖 | 被更高优先级剧本覆盖 |

### 4.5 Decision Engine 输出协议

Decision Engine 不负责预测价格，而负责编排事实、规则、剧本和风险约束。统一输出：

```json
{
  "action": {
    "type": "hold",
    "label": "继续持有",
    "target_quantity": 100,
    "execution_zone": null
  },
  "reason": [
    "MA5 首次跌破，尚未满足两根 5 分钟 K 确认",
    "个股重新站回 VWAP，分时承接恢复",
    "所属板块未进入退潮状态"
  ],
  "current_scenario": {
    "scenario_id": "ma5_low_open_reclaim",
    "label": "低开缩量后收回",
    "match_level": "high"
  },
  "switch_conditions": [
    {"when": "第二根 5 分钟 K 仍收于 653.4 下方", "to": "risk_exit"},
    {"when": "放量突破 669.8 并保持一根 5 分钟 K", "to": "breakout_hold"}
  ],
  "evidence": [],
  "data_freshness": {},
  "computed_at": "2026-07-13T10:15:02+08:00"
}
```

首版禁止输出未经历史校准的“74% 发生概率”。允许显示：

- `match_level`：低、中、高，由满足的必要条件和加分条件确定。
- `evidence_completeness`：已获得证据数/所需证据数。
- `rule_trace`：命中、未命中和等待确认的具体规则。

### 4.6 硬规则优先级

规则分为五层，从高到低执行：

1. 数据安全：按动作类型检查数据；数据缺失、延迟或时间戳倒退时停止对应类型的新动作。
2. 硬风险：硬止损、最大亏损金额和禁止操作权限。
3. 剧本失效：当前 Scenario 的必要条件被破坏。
4. 剧本匹配：按必要条件、确认条件和互斥条件选择当前 Scenario。
5. 展示解释：生成 Action、Reason、Evidence 和切换条件。

同一时刻只允许一个 `current_scenario` 和一个主 Action。其他剧本保留为候选、等待、失效或被覆盖状态。P0 把 Action 分为：

- 主动型：持有、观察、突破持有和准备减仓，需要个股报价、已收盘 5 分钟 K、上证和创业板数据可信；板块是可选增强证据。
- 防御型：硬止损，只要求个股报价和已收盘 5 分钟 K 可信，不因指数或板块短暂故障而延误。

## 5. 图形区域诊断

系统只判断技术图形，不输出基本面结论。

| 类型 | 初版指标口径 | 允许评估的手法 |
|---|---|---|
| 高位被套 | 买入价处于前 120 日区间前 20%；偏离 MA20 超过动态 ATR；冲高回落或板块退潮 | 持有观察、反弹处理、倒 T 候选、止损 |
| 箱体被套 | MA20 斜率接近 0；ADX 偏低；价格仍在识别出的箱体上下沿内 | 箱体持有、压力倒 T、支撑接回 |
| 低位被套 | 位于前 120/250 日区间后 30%；没有继续创新低；缩量或出现均线收回 | 持有观察、企稳后补仓候选 |
| 结构破坏 | 硬止损、MA60 或重要前低被确认跌破且未收回 | 关闭倒 T、补仓和迁移，进入风险动作 |
| 不确定 | 数据不足或多项条件冲突 | 只显示事实，不给主动动作 |

所有阈值进入策略参数，不在 UI 文案中硬编码。

## 6. 双指数与板块

### 6.1 大盘拆分观察

驾驶舱分别显示并计算：

| 对象 | 主要用途 |
|---|---|
| 上证指数 `000001.SH` | 全市场与沪市权重环境、关键位、成交趋势 |
| 创业板指 `399006.SZ` | 成长风格和风险偏好、科技方向情绪 |

不把两者预先合并为一个黑盒总分。周一版不计算个股与指数的滚动相关性或预测敏感度；两个指数始终分别展示，并按明确阈值标记修复、震荡、分歧或走弱。

### 6.2 个股板块

默认使用持仓记录中的 `sector_name`；没有人工覆盖时回退当前板块映射。板块至少输出：

- 日线阶段：主升、修复、分歧、退潮。
- 当日涨跌与成交活跃度。
- 个股相对板块强弱。
- 板块与上证/创业板的盘中共振。
- 数据来源和更新时间。

### 6.3 周一实时数据主链路

周一版优先使用 KlineShare：

```text
KlineShare /v1/realtime
├── 活动持仓批量报价
├── 上证指数 000001.SS
└── 创业板指 399006.SZ

KlineShare /v1/kline?period=300&adjust_type=none
├── 活动持仓 5 分钟 K
├── 上证指数 5 分钟 K
└── 创业板指 5 分钟 K
```

内部 ticker 继续使用 `.SH/.SZ`；只有在 KlineShare HTTP 边界把上海市场转换为 `.SS`。`000001` 裸代码存在歧义，任何请求都必须携带交易所后缀。

接入规则：

- API Key 只通过 `X-API-Key` 请求头发送，不放入查询参数和日志。
- 必需 scope：`realtime`、`kline`；启动前调用 `/v1/me` 回读权限。
- 实时批量优先把持仓和双指数合并请求，减少调用次数。
- 5 分钟 K 使用 `period=300`、`adjust_type=none`，只保存确定已经收盘的 K。
- 429 必须读取 `retry_after/Retry-After`，不得立即重试形成请求风暴。
- KlineShare 未配置或暂时失败时，现有新浪实时和 AKShare 分钟接口只作为显式降级源，并在页面展示真实来源。

2026-07-11 公开 catalog 显示基础版：实时单次最多 20 个 symbol、实时行情 60 次/分钟、K 线 300 次/分钟、每分钟最多 200 个不同品种。当前持仓规模足够，但运行时仍以 `/v1/me` 返回为准。

## 7. 首个 Playbook：MA5 Trend v0.2

### 7.1 关键原则

- 跌破 MA5 是输入，不等于立即减仓。
- 软破位等待连续两根 5 分钟 K 确认。
- 日线 MA5/MA10/MA20、支撑、压力和硬止损在开盘前冻结，盘中不能移动底线。
- 实时估算 MA 可以辅助解释，但不能覆盖冻结的风险线。
- 大盘和板块可以降低目标仓位，但不能降低硬止损底线。

### 7.2 状态

```text
above_ma5
→ testing_ma5
→ below_ma5_pending
→ ma5_reclaimed 或 ma5_break_confirmed
→ structure_failed
```

### 7.3 开盘与承接

周一版高开、平开、低开优先使用昨收的固定百分比阈值，阈值进入配置；已有可靠 ATR 时才允许使用 ATR 参数，不为此新增测算链路。盘中至少观察：

- 开盘缺口。
- 前 30 分钟相对开盘价与 VWAP 的位置。
- 连续 5 分钟 K 收盘位置。
- 5 分钟成交量相对历史同时间段。
- 跌破后的收回速度。
- 个股相对所属板块、上证和创业板强弱。

### 7.4 默认 Scenario List

| 优先级 | P0 剧本 | 主要触发 | 输出 |
|---:|---|---|---|
| 100 | 硬止损 | 硬止损/结构破坏确认，或风险金额将被突破 | 风险预算允许的最大目标数量 |
| 80 | MA5 破位 | 连续两根 5 分钟 K 跌破且未收回 | 动态目标数量与处理区间 |
| 75 | 放量突破前高 | 5 分钟 K 突破前高且量比达到配置阈值 | 继续持有 |
| 70 | 跌破后快速收回 | 前一根低于 MA5、当前收回冻结 MA5 | 破位剧本失效，继续持有 |
| 60 | 低开承接恢复 | 低开后重新站上 VWAP 与冻结 MA5 | 继续持有或等待承接确认 |
| 20 | 原计划持有 | 以上剧本均未成为当前剧本 | 保持目标数量并展示环境风险 |

高优先级剧本触发后，低优先级剧本标记为 `suppressed`。

倒 T、补仓和策略迁移继续保留为 P1 Playbook 扩展，不进入周一 P0。周一版每条规则必须可以用当前价、昨收、开盘价、冻结关键位、5 分钟 K、成交量、VWAP、指数和可用板块状态直接计算。不得要求训练、拟合或离线特征工程。

## 8. 动态绝对金额风控

### 8.1 原则

止损使用绝对金额，不使用固定亏损率。系统不得输出固定“减仓 20%/50%”。

定义：

- `Q`：当前持仓数量。
- `q`：调整后的剩余数量。
- `C`：实际成本价。
- `P`：当前可成交参考价。
- `S`：当前有效止损价。
- `R`：本笔交易已实现亏损。
- `F(q)`：预计费用和滑点。
- `Lmax`：单笔最大允许亏损金额，当前为 6,880 元。

候选动作的最坏损失：

```text
worst_loss(q)
= R
+ max(0, C - P) × (Q - q)
+ max(0, C - S) × q
+ F(q)
```

系统枚举可交易数量，选择满足以下条件的最大 `q`：

```text
worst_loss(q) <= Lmax
```

最终数量：

```text
risk_allowed_qty = 风险预算允许数量
playbook_target_qty = 当前剧本规则允许数量
market_cap_qty = 双指数硬规则允许的数量上限
sector_cap_qty = 板块硬规则允许的数量上限

final_target_qty = tradable_round(
    min(risk_allowed_qty, playbook_target_qty, market_cap_qty, sector_cap_qty)
)
change_qty = current_qty - final_target_qty
```

若硬止损已经确认，Playbook 可以把 `playbook_target_qty` 降为 0；但最终动作仍需经过交易单位和当前可成交价格计算，不在代码里写死股票数量。

### 8.2 页面解释

```text
当前数量：100 股
有效止损：X
当前全部卖出预计亏损：A 元
保持至止损预计总亏损：B 元
最大允许亏损：6,880 元
```

## 9. Trading 工作空间与交易驾驶舱

### 9.1 持仓总览

| 股票 | Playbook | 当前剧本 | 当前动作 | 下一切换条件 | 数据状态 |
|---|---|---|---|---|---|
| 兆易创新 | MA5 Trend v0.2 | 低开承接 | 暂不处理 | 连续两根 5 分钟 K 跌破 X | 正常 |

每行第二层显示大盘、板块、个股的独立状态，不生成综合分：

```text
上证：修复｜创业板：分歧｜半导体：修复｜个股：支撑观察
```

表格只显示当前最高优先级动作。点击行进入单票驾驶舱。

### 9.2 单票驾驶舱阅读顺序

1. **Action**：当前动作、目标数量、建议变动、操作区间和风险金额。
2. **Reason**：按重要性列出判断变化的原因，不先展示指标名称堆栈。
3. **Scenario**：当前剧本、匹配等级、等待条件、失效条件和切换目标。
4. **Evidence**：关键位、5 分钟 K、成交量、VWAP、冻结均线和规则轨迹。
5. **Market**：上证、创业板、所属板块和个股四张独立状态卡。
6. **Raw Data**：图表、原始行情、时间戳和数据来源，可折叠展开。
7. **Decision Timeline**：记录系统判断为何变化。
8. **用户确认**：已查看、已执行、忽略一次、调整计划。

股票标题和持仓卡可显示股票 Logo。P0 使用百度证券静态资源规则 `stock_ab_{6位代码}.svg`；外部资源加载失败时自动隐藏图片并回退为股票名称首字，不得影响标题、行情和决策内容。

第一屏不得以 MA5、MACD、KDJ 或 K 线图作为视觉中心。第一屏必须同时显示当前 Action、当前 Scenario 和明确的切换条件。

“下一次需要操作预计”改为“最早确认时间”，只根据下一根 5 分钟 K 的确定收盘时间计算，不预测市场将在何时触发动作。

### 9.3 Decision Timeline

时间线仅在决策发生实质变化时新增记录，避免每次轮询制造噪声：

```text
09:35 继续持有
原因：低开但成交量未放大，首次跌破尚未确认

09:52 切换为等待观察
原因：创业板跌破早盘低点；当前剧本由“低开承接”切换为“弱势确认中”

10:07 恢复持有
原因：板块率先修复，个股重新站回 VWAP，破位剧本失效
```

每条记录持久化：前后 Action、前后 Scenario、变化原因、命中规则、关键证据快照、Playbook 版本、数据时间和计算时间。

### 9.4 数据状态

| 状态 | 规则 | 系统行为 |
|---|---|---|
| 正常 | 个股/双指数报价不超过 45 秒；5 分钟 K 不超过 7 分钟；板块不超过 2 分钟 | 正常计算 |
| 延迟 | 任一关键数据超过阈值 | 保留上一判断并标记过期 |
| 缺失 | 对应动作的必要数据缺失；时间戳倒退；时间戳超前超过 5 秒 | 停止生成该类型的新操作建议 |
| 休市 | 非交易时段 | 展示开盘前/收盘后预案 |

P0 主动型动作的必需来源固定为：`stock_quote`、`stock_5m`、`index_sse_quote`、`index_chinext_quote`；`sector_quote` 为可选增强。防御型动作只要求 `stock_quote` 和 `stock_5m`。数据状态为延迟或缺失时，可以展示最后一次有效判断，但该判断必须标记为过期，且不得包装成不满足数据要求的新 Action。

所有报价同时保存：

- `quote_at`：数据源给出的真实行情时间，用于新鲜度判断。
- `fetched_at`：本系统完成抓取的时间，只用于链路监控。

禁止使用 `fetched_at` 冒充 `quote_at`。只有快照日期、没有盘中行情时间的板块数据不得标记为实时。

## 16. 实施记录与逐 Job 反思

### 16.1 Job 1：P0 契约与数据安全门（2026-07-11，已完成）

实际产出：

- 建立独立 `shilun.trading` 边界，未直接改写旧研究决策模块。
- 冻结 `TradingFacts`、`RuleTrace`、`ScenarioCandidate`、`TradingAction`、`DecisionResult` 契约。
- 冻结规则版本 `trading-p0-v0.2.0`，确认周期为 5 分钟、软破位 2 根、硬止损 1 根。
- 集中配置高低开、确认 K 数、放量和数据新鲜度阈值。
- 数据缺失、延迟、时间戳倒退或异常超前时，禁止生成新 Action。
- 新增 12 个契约/安全门测试；连同策略、分时共振、持仓和持仓事件相关回归共 62 项通过。

实施后对 PRD 的修正：

1. “数据缺失”不只包含空值，还必须包含时间戳倒退和明显的未来时间，否则旧缓存或乱序写入可能产生错误动作。
2. 数据新鲜度必须按来源分别配置，不能只写一个笼统的实时阈值。
3. 数据不安全时保留“最后有效判断”和“生成新判断”是两件事；P0 契约只允许前者展示为过期，不允许后者伪装为当前动作。
4. 旧研究决策层仍包含概率和模型字段。周一前不做破坏性删除；Trading 使用新边界隔离，旧模块退场放到 P1。

当前反思：

- v0.2 不是理论上的最终最优解，而是当前交付窗口下的最优候选。它的价值在于边界清楚、规则可审计、后续可替换。
- 独立新建 Trading 领域比立即重构旧 Decision 层更安全，但形成了短期双轨。必须在 P1 明确迁移和删除计划，避免永久并存。
- `sector_quote` 当前被列为必需来源，安全但偏保守。Job 2 回放时需验证：板块数据短暂延迟是否应阻止所有风险动作，还是只阻止主动动作、仍允许硬止损。这是下一 Job 最值得优化的规则分层。
- 目前只有“是否允许生成新动作”的总闸门。下一 Job 应把动作分成防御型与主动型，验证硬止损是否可以在板块数据缺失、但个股价格可信时继续触发。

暂停点：Job 1 完成后停止，不自动进入 Job 2。下一步经确认后实施 MA5 Trend Playbook、双指数/板块事实和防御型动作的数据降级策略。

### 16.2 Job 2：数据源审计、动作降级与 MA5 Playbook（2026-07-11，已完成）

#### 数据源运行态结论

| 数据 | 现有来源与实测 | 是否支撑周一盘中 | P0 处理 |
|---|---|---|---|
| 个股实时报价 | Tushare 封装的新浪源；实测可返回兆易创新，原始响应包含真实 `date/time` | 支撑 | 主数据源；使用 `quote_at` 判断时效 |
| 上证/创业板实时报价 | 同一新浪接口可批量返回双指数，原始响应包含真实 `date/time` | 支撑 | 与个股同批/近同时抓取，分别展示 |
| 个股与指数 5 分钟 K | AKShare `stock_zh_a_minute`（新浪源）；兆易创新实测返回 1970 行，最新到 2026-07-10 15:00 | 上游支撑，现有任务不支撑盘中 | 新增活动持仓 + 双指数盘中采集；只使用已收盘 K |
| Mongo 分钟线 | `minute_bars_daily` 实有 124 个文档，最新交易日 2026-07-10；双指数存在，但兆易创新不存在 | 当前不支撑全持仓盘中 | 不能直接作为周一实时输入，需要扩大采集范围和频率 |
| 板块日内行情 | AKShare/东方财富存在行业与概念板块分钟接口，但本机多次实测发生断连/代理错误 | 不足以作为硬依赖 | P0 降为可选增强，缺失显示 unknown |
| 板块映射 | 兆易创新持仓 `sector_name` 为空；`stock_basic.industry` 可回退为“半导体”，但没有可靠概念板块成员映射 | 仅支撑静态行业回退 | P0 展示静态行业；概念板块映射进入 P1 |
| 日线与冻结关键位 | Mongo `market_daily_bars` 约 148 万条，已有 MA5/MA10/前高等计算链路 | 支撑 | 仅在开盘前冻结，不作为伪实时数据 |

本次实测还发现：休市日调用新浪报价会返回上一交易日收盘数据。原适配器丢弃源 `date/time`，并把本次抓取时间写为 `update_at`，会把旧行情误判成实时。现已修正为：

```text
quote_at   = 数据源真实行情时间
fetched_at = 本系统抓取完成时间
update_at  = quote_at（兼容旧调用方）
```

#### 实际产出

- 新增主动型/防御型 Action 数据要求：主动型依赖个股 + 5 分钟 K + 双指数；防御型只依赖可信个股事实。
- `sector_quote` 从硬依赖调整为 P0 可选增强，缺失时产生降级原因但不阻断主动判断。

1. 当前策略只看“本交易日一根 5 分钟 K 是否跌破硬止损”；新判断要求硬止损一旦确认就跨交易日保持为待执行风险动作，直到成交回写。该跨日风险锁已在本轮补充实现，不再允许下一交易日因价格恢复而自动回到“继续持有”。
2. 当前动态数量计算只约束单笔最大亏损；新判断还关注单名仓位占账户约 71.2% 的集中度。即使亏损预算未突破，这个仓位也不应被视为普通风险状态。
3. 系统现已补充 `trade_executions` 成交回写：可记录已经发生的卖出股数、均价、费用和时间，并更新剩余股数、已实现亏损和风险动作状态。它只记录成交事实，不连接券商、不自动下单。
4. 当前板块状态仍可能为 `unknown`，但这不应阻止已确认硬止损；它只影响主动持有、倒 T 或加仓判断。

Trading 完整度反思：

#### KlineShare 交易日历方案

1. 每月同步未来 366 天并保留 `source=klineshare`；Tushare 可作为对账源，不在业务层双重回退。

这项重构能减少日期处理重复，但不能直接删除所有日期函数；应删除的是散落的周末/自然日算法，保留一个统一交易日历服务。

### 16.16 Job 10 热修：KlineShare 盘中事实链路验收（2026-07-13，已完成）

### 16.19 Job 12 讨论稿：持仓决策与机会发现双引擎（2026-07-14，未批准、未执行）

本节只记录讨论结论与待决策项，不代表进入开发；所有任务保持未执行状态。

#### 现有语义缺口

1. `TradingDecisionService` 当前以 holdings 文档的 `status=active/reduced` 判定持仓身份，真实股数为空只会导致 `quantity_not_configured`，不会自动变成空仓。因此“有持仓记录但数量为空”目前是状态未知，不是已证明空仓。
2. 盘中候选的 `intradayActionSummary` 没有读取真实持仓状态；`support_reclaimed / ma8_reclaim / pressure_breakout` 会统一映射为“继续持有并观察确认”。这对空仓候选是错误语义：结构修复不等于已经持有，也不等于允许建仓。
3. 当前已经有持仓 Decision Engine，也有 MA5 单票 `candidate/watch` 评估，但缺少把全市场筛选、盘中触发、风险可实施性和组合约束串起来的 Opportunity Engine。

#### 建议先建立一等公民的 Position State

| 状态 | 硬定义 | 允许动作 |
|---|---|---|
| `positioned` | `quantity > 0` 且持仓生命周期为 active/reduced | 持有、加仓候选、减仓、退出 |
| `flat` | 用户显式标记空仓，或已完成清仓回写 | 等待、准备建仓、建仓触发、不追/错过 |
| `unknown` | 存在 active/reduced 记录但 `quantity` 为空，或成交事实不完整 | 禁止输出数量动作；先确认持仓事实 |
| `closed` | 已关闭的历史持仓 | 只用于复盘；重新关注需进入 watchlist |

关键约束：`null` 不能默认为 0。页面应提供“确认股数”和“标记为空仓”两个显式动作，避免系统擅自把未知状态解释为空仓或持仓。

#### 双引擎职责边界

**Position Decision Engine（已持仓）**

- 回答：是否持有、减仓、退出，若动作改变需要卖多少股。
- 优先消费真实数量、成本、可卖数量、有效止损、策略失效条件和待执行成交。
- “继续持有”只允许对 `positioned` 输出；没有真实股数时不得输出。

**Opportunity Engine（空仓候选）**

- 回答：为什么现在进入候选、是否已满足入场条件、最高可接受价格、失效位、初始风险预算，以及为什么它排在其他候选之前。
- 第一阶段只输出 `仅观察 / 接近触发 / 建仓条件已触发 / 不追或已错过 / 禁止开仓`，不直接连接券商。
- Screen 结果只能叫候选或研究优先级，不能因综合分高就自动变成买入建议。

#### 机会发现漏斗

当前 KlineShare 同分钟不同品种额度约 200，只能支持定向盘中监控，不能用当前套餐对全 A 市场逐票实时扫描。建议采用分层漏斗：

```text
全市场已完成日线
  → 大盘开仓权限
  → 板块/流动性/基础排除
  → Playbook 日级 Setup 候选
  → 盘前冻结 100–198 只监控清单（为双指数预留额度）
  → KlineShare 实时价与 5 分钟 K
  → 入场触发与取消条件
  → 机会队列 Top N
```

这意味着未来应区分：

- `discovery_universe`：全市场日级发现池；负责发现新机会。
- `execution_watchlist`：当日有限的盘中监控池；负责等待触发。
- `holdings`：真实持仓；负责风险处置。

用户手工选品池不应成为唯一发现来源；系统可以从 discovery universe 自动晋级到 execution watchlist，但不得自动建仓。

#### 建仓资格硬门槛

只有同时满足以下条件的空仓候选，才进入“可建仓”队列：

1. `position_state=flat`，且行情和 5 分钟 K 在安全新鲜度内。
2. 大盘 `entry_permission` 允许开新仓；风险退出可以绕过市场 Gate，但新开仓不可以。
3. Playbook 日级 Setup 有效，盘中 Trigger 已确认；仅有“结构良好”不够。
4. 入场区、失效/止损位和目标位均已定义，计划盈亏比至少达到策略门槛（MA5 当前为 2:1）。
5. 当前价没有超过 `max_acceptable_price`；高开过多、触发后快速拉升或错过确认时输出“不追/已错过”。
6. 可用现金、单笔风险、总开放风险、板块集中度和组合相关性允许新增风险。
7. 流动性、涨跌停状态和数据覆盖没有阻断。

排序不建议只给一个黑箱综合分。先按硬门槛分层，再在同层内按以下顺序排序：

`触发状态 → 触发新鲜度 → 计划盈亏比 → 个股相对强度 → 板块共振 → 距入场区 → 流动性`。

#### 盘中动作优先级

页面不应把所有股票混成一条“总分榜”，建议保留四条并行队列：

1. **风险处置**：已持仓硬止损、退出、减仓、待成交回写。
2. **建仓机会**：空仓且全部硬门槛通过、入场触发已确认。
3. **接近触发**：Setup 有效但仍差一项盘中确认，显示下一条件和距离。
4. **无动作/不可交易**：继续持有但无变化、普通观察、市场禁止开仓、已错过或数据不完整。

若必须形成单一通知顺序，则使用：

`持仓硬退出 > 持仓减仓 > 已触发的合格建仓 > 合格加仓 > 接近触发 > 无变化持有 > 普通观察`。

但首屏应同时展示“风险处置数量”和“可建仓机会数量”，避免风险事件把机会发现完全淹没。

#### 空仓机会卡的最小信息

```text
长电科技 · 空仓
状态：接近建仓触发（不是继续持有）

还差：一根闭合 5 分钟 K 站稳 VWAP / 关键位
计划入场区：xx–xx
最高可接受价：xx
失效位：xx
目标位：xx
计划盈亏比：x.xx
大盘权限：允许 / 禁止
板块状态：主升 / 修复 / 分歧
若现在追入：不满足，等待或放弃
```

初始股数只能在组合风险约束完整时计算；缺少现金、总开放风险或持仓状态时显示“规模待组合校准”，不能把单票信号直接换算成买入股数。

#### 从交易员视角发现的其他不合理点

1. **研究优先级和执行优先级混在一起**：高分股票可能值得研究，但尚未出现可交易价格；临近触发的中等分股票反而更需要盘中关注。
2. **选品池是封闭池**：只能监控已选股票，不能回答“今天市场新出现了什么”。需要全市场日级发现池与盘中有限监控池两级结构。
3. **缺少组合级风险预算**：当前主要控制单笔最大亏损；没有可用现金、总开放风险、行业集中度、相关持仓和单日亏损上限，就无法判断多个候选中谁“最值得建仓”。
4. **当前示例风险配置需要保护性提示**：账户 86,000 元、单笔最大亏损 6,880 元相当于净值的 8%。系统至少应显示比例、缺口/滑点压力情景和高风险告警，而不能只显示“已配置”。
5. **缺少可卖数量与成交批次**：总股数不等于盘中可立即卖出的数量；执行层需要持仓批次、当日成交、冻结/可用数量和部分成交状态，不能只用一个 `quantity`。
6. **缺少追价保护与机会过期**：触发发生后价格已远离入场区时，应自动切换为“不追/已错过”，而不是继续保留正向动作。
7. **入场与退出确认不应对称**：硬止损应立即升级；新建仓建议至少等待一根闭合 5 分钟 K 或两次独立快照确认，降低盘中噪声误触发。
8. **没有明确的机会成本解释**：Top1 应说明“为什么它高于 Top2”，包括更近的触发、更好的盈亏比、更强的板块共振或更低的组合冲突。
9. **通知通道需要分级**：风险退出、建仓触发和普通接近条件不应使用同一种飞书样式和频率；风险必须强提醒，机会可合并，普通观察只留页面。

#### 待用户确认的产品决策

1. 空股数默认保持 `unknown`，并提供显式“标记为空仓”（建议）；还是把空股数直接视为 0（不建议）。
2. 机会发现是否采用“全市场日级自动晋级 + 盘中最多约 198 只定向监控”（建议）；还是只监控用户手工选择。
3. 新建仓触发是否统一采用“一根闭合 5 分钟 K 确认”（建议）；不同 Playbook 后续可覆写。
4. 风险配置是否增加净值百分比、总开放风险、单日亏损和行业集中度四个组合级约束（建议）。
5. 加仓是否进入第一版 Opportunity Engine；建议第一版先完成空仓首仓，待真实成交批次和组合风险稳定后再做加仓。

### 16.20 Job 12 讨论修订：从“选品策略”补齐“执行策略”（2026-07-14，规则稿 v0.3，未执行）

详细的状态依据、中文指标与动作、阈值来源、数据源、E1–E7 全场景规则、Job 拆解与验收标准已独立整理为 [`execution_playbook_project_plan.md`](execution_playbook_project_plan.md)。独立文档 v0.3 为当前 Job 12 的唯一规则主稿；本节下方的方向性摘要只保留架构脉络，若两处冲突，以独立讨论稿为准。

本节修订 16.19 的重点：最高可接受价、机会过期、入场确认、可卖数量等都不是彼此独立的页面功能，而是 **Execution Playbook（执行剧本）** 的组成部分。当前系统已经投入较多工程复现市场、板块和个股状态，也能用 MA5 等规则筛出候选，但缺少从“候选”走到“建仓、持仓、减仓、退出”的状态化执行层。

#### 产品分层

```text
市场与研究事实
  → Selection Playbook：选什么、为什么进入候选
  → Execution Playbook：何时允许动、以什么价格、多少股、何时取消
  → Execution State：当前走到哪一步
  → Action + Quantity：用户此刻要做什么
  → 成交回写 / Decision Timeline：动作是否执行、判断为何改变
```

Selection Playbook 的高分不能直接翻译为买入；每个通过筛选的候选必须先生成一份当日冻结的 `ExecutionPlan`。同一个 Selection Playbook 可以绑定多个执行剧本，例如 MA5 回踩收复与前高突破不能共用一套触发条件。

#### ExecutionPlan 最小契约

| 字段 | 用途 |
|---|---|
| `plan_id / ticker / trade_date` | 唯一定位当日执行计划 |
| `strategy_id / strategy_version / execution_playbook_id` | 固定选品与执行规则版本，支持复盘 |
| `position_state` | `flat / unknown / positioned / closed`，决定允许的动作词汇 |
| `setup_type` | 回踩收复、突破、持仓保护等剧本类型 |
| `entry_trigger` | 进入确认阶段的客观条件 |
| `entry_confirmation` | 新建仓需要的闭合 K 或独立快照条件 |
| `entry_zone / max_entry_price` | 允许成交区与追价上限 |
| `cancel_conditions / expires_at` | 剧本失效与机会过期条件 |
| `initial_stop / targets / min_rr` | 初始失效位、目标与最低盈亏比 |
| `planned_quantity / planned_cash / max_loss` | 由风险与现金共同约束的计划仓位 |
| `reduce_rules / exit_rules` | 建仓后沿用的减仓和退出条件 |

`max_entry_price` 不应手工写一句“不追”。它应由执行计划计算：同时满足入场区上沿、最低盈亏比和允许滑点三项约束，取其中最严格者；价格越过后状态切换为 `missed`，不再继续输出正向动作。

#### 执行状态机

```text
selected
  → armed
  → confirming
  → entry_ready
  → entry_pending
  → positioned
  → hold / reduce_pending / exit_pending
  → closed

任一建仓前状态
  → expired / cancelled / missed / data_blocked
```

状态语义：

1. `selected`：只完成日级选品，不占用盘中执行优先级。
2. `armed`：市场权限、板块状态、关键价位和数据覆盖都允许开始监控。
3. `confirming`：触发已发生，等待执行剧本规定的确认；这是“接近建仓”，不是买入。
4. `entry_ready`：确认完成、价格未越过上限且现金可用，才允许显示“可建仓”。
5. `entry_pending`：用户已下单或已记录委托，等待实际成交回写；避免重复提醒和重复占用现金。
6. `positioned`：只在真实买入成交写回后进入；此后才允许“继续持有、减仓、退出”。
7. `missed / expired`：追价上限被越过或当日有效期结束，释放预留现金，等待下一份计划。
8. `data_blocked`：数据不安全时禁止新建仓；可信的硬止损事实不应因外围数据缺失而被静默降级。

因此，空仓的长电科技绝不能显示“继续持有”：它只能处于 `selected / armed / confirming / entry_ready / missed` 之一；股数为空且用户没有确认空仓时为 `unknown`，禁止计算买卖数量。

#### MA5 Execution Playbook v0.1 建议范围

第一版只做两类入场剧本和一类持仓保护，不引入时序模型或分类模型。

**A. 回踩收复**

- 前置：MA5 Selection Playbook 仍有效，大盘允许新开仓，板块没有进入明确退潮。
- 触发：价格进入 MA5/MA8 或既定关键位附近的入场区。
- 确认：一根闭合 5 分钟 K 收回执行关键位；VWAP、个股相对强弱和板块同步用于规则确认或否决。
- 可执行：当前价仍在 `max_entry_price` 内，计划盈亏比仍达标，现金和单笔风险允许。
- 取消：关键结构失效、板块/大盘关闭新仓权限、超过追价上限或计划到期。

**B. 突破确认**

- 前置：日级 Setup 有效，前高/压力位已在盘前计划中冻结。
- 触发：价格突破关键位。
- 确认：一根闭合 5 分钟 K 保持在关键位之上，并满足执行剧本规定的量价与板块共振条件。
- 可执行与取消：沿用价格上限、盈亏比、现金、风险和过期约束。

**C. 持仓保护**

- 硬止损或明确结构失效：立即升级为退出，不等待与入场相同的确认。
- 一般走弱：可等待闭合 5 分钟 K 或连续快照确认后减仓，具体由 Playbook 配置。
- 未触发风险规则：继续持有，但“持有”不进入机会榜抢占注意力。

精确的价差、成交量、VWAP 和相对强弱阈值暂不在 PRD 中拍定，应使用已有历史日线和真实 5 分钟 K 做回放，比较误触发、错过率与最大不利波动后再冻结为版本参数。

#### 仓位与风险 P0 简化

不在第一版建设完整组合风险平台。总开放风险、行业集中度、相关持仓和压力测试暂不进入 Job 12。风险配置只保留执行所需的四个事实：

1. 账户净值；
2. 可用现金；
3. 单笔最大亏损；
4. 单票现金上限（可选，缺省受可用现金约束）。

配置区只需一行显示：`单笔最大亏损 ¥6,880 / 净值 ¥86,000 = 8.0% · 高风险`，不展开复杂压力测试。计划股数取下列两项的较小值并按交易单位取整：

```text
风险允许股数 = 单笔最大亏损 ÷（计划入场价 - 初始止损价 + 费用/滑点缓冲）
现金允许股数 = min(可用现金, 单票现金上限) ÷ 计划入场价
计划股数     = min(风险允许股数, 现金允许股数)
```

多个机会同时触发时，不能让每只股票都重复使用同一笔现金。第一版采用“1 个主机会 + 2 个备选”：`entry_ready` 的主机会预留计划现金；它成交、取消或过期后再向下一只释放。暂不计算行业和相关性。

#### 盘中机会优先级

先按执行状态分层，不再直接按选品总分排序：

```text
P0 已持仓硬退出
P1 已持仓减仓 / 待成交处理
P2 空仓 entry_ready（主机会）
P3 空仓 confirming / 接近触发
P4 armed / 普通监控
P5 持有无变化 / selected
```

同为 `entry_ready` 时再比较：触发新鲜度、距最高可接受价、计划盈亏比、板块共振、个股相对强弱和流动性。页面必须解释 Top1 为什么排在 Top2 前，而不是只显示一个综合分。

#### 复用现有工程

1. PART1、大盘权限、板块状态、日线指标和 MA5 评分继续负责发现与盘前 Setup，不重做市场复现工程。
2. KlineShare 实时价与闭合 5 分钟 K 只监控当日冻结的 `execution_watchlist`，驱动状态变化；页面刷新不直接触发外部接口。
3. 现有 `trading_watch_plans` 可扩展为冻结的 `ExecutionPlan`，现有 `DecisionResult / RuleTrace / ScenarioCandidate` 继续承载原因、证据与剧本；不另造一套平行解释系统。
4. `decision_timeline` 改为记录 Execution State 的变化事件；飞书只推送状态升级、取消、过期和风险动作，不重复推送无变化快照。
5. 现有卖出成交回写保留，但执行闭环需要补齐买入委托/成交回写，只有真实成交才能把状态改为 `positioned` 并占用真实现金。

#### v0.3 已确认的实现边界

1. 第一版覆盖低开修复、均线回踩、区间反转、箱体突破、弱转强、高开突破和超跌反弹隔夜套利，不缩为单一回踩场景。
