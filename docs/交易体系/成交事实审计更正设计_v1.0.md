## 3. 用户操作闭环

1. 从“已提交批次”或具体成交打开审计更正，显示原件、原行、原始事实、当前有效事实、历史版本及共享该事实的全部批次。正常导入预览仍可取消，不产生事实写入。
2. 明确选择要更正的事实行和动作，填写完整替代值、独立原因及可恢复证据；可引用已归档来源，也可上传新原件。数量连带变化、拆分/合并与缺单一起提交，不能按行生效到一半。
3. 只读预览差异：原值/当前值/拟议值，数量与现金对账，费用与收益变化，未知状态，旧/新库存轮、FIFO 批次及受影响引用。
4. 对每个受影响引用明确选择“保留历史、待核映射”或提交具体映射；查看共享事实范围与不能核实的缺口。未映射不是把错误事实永久留在当前账本的理由，但必须保留历史并生成可操作待办。
5. 用户确认该份预览后，服务端锁内重读、核对预期版本与摘要并提交；页面显示更正回执、前后账本版本、待核引用及原件入口。修改表单或底层事实变化使预览失效，必须重做。
6. 重开页面仍能恢复同一结果；后续可逐项重新分配、重核复盘、重做成交匹配。撤销时重新预览影响，再追加反向更正。

页面须区分“原始归档”“当前更正结果”“更正前历史版本”，不得只在原始 JSON 中藏版本或 stale 状态。历史查看默认只读，不能把历史版本的编辑表单当成当前写入上下文。

## 4. 事实版本与持久合约

拟新增 `JournalCorrectionService(store, journal=...)`，写入范围限定 `trade_journal_*`。主要逻辑实体如下；物理分片方式在实现时按 BSON 预算确定，不能截断原件、行、引用或名单。

| 实体 / 建议集合 | 必须保存的内容 |
|---|---|
| 更正回执 `trade_journal_corrections` | 更正 ID、请求摘要、顺序/前驱摘要、预期事实版本、操作全集、原因、作者原文及可核实操作者、服务端记录时间、证据引用、前后账本引用、受影响引用处置、可选 `reverses_correction_id`、内容 hash。 |
| 账本版本 `trade_journal_ledger_revisions` | 版本摘要、精确批次回执集合、更正链、有效事实版本引用、FIFO 算法版本、受影响库存轮的前后内容与 hash，以及恢复完整结果所需的清单。 |
| 关联事件 `trade_journal_reference_bindings` | 被映射 owner/对象 ID/确切 revision/hash、原账本版本、目标库存轮和当前事实版本、明确股数/成交子集、原因、服务端记录时间、前驱与内容 hash。 |

单个更正操作的最低合约：

```json
{
  "kind": "fills",
  "fact_id": "原逻辑canonical ID",
  "action": "replace",
  "expected_fact_revision": 0,
  "expected_effective_fact_hash": "读取时摘要",
  "replacement": {},
  "source_refs": [],
  "reason": "本行更正原因"
}
```

- `replace`：同一逻辑事实追加有效版本，保留 canonical ID；原集合不覆盖，不把原件解释成被改写。
- `void`：将该事实退出当前有效投影，原事实、来源及批次仍可恢复；须说明作废依据及全部共享影响。
- `add`：审核漏单或结构替代后新增逻辑事实，明确来源与前驱关系，不能以近似价量自动拼身份。拆分/合并保存完整旧→新对应，原事实退出与新事实进入同一可见提交。

操作同时支持 `financial_events`。普通买卖与公司行为/资金事件仍分别规范化；股票入账、IPO 缴款成本及关联证券须联动检查，不能把非交易现金塞进普通买卖。

替代版本保存在更正实体或其不可变分片中，**不以新内容覆盖 `trade_journal_fills` 的同 ID 记录**，也不靠另造 fill ID 绕开券商成交身份唯一约束。

新增 `effective_fact_hash` 覆盖全部影响计算与身份判定的有效字段，至少包含日期、实际时间及可信度、证券/账户、方向、数量、金额、费用、净现金、报告余额和 `inventory_order`。现有 fill 的 `content_hash` 排除了 `inventory_order`，不能直接充当完整更正指纹。原来源证明与新来源证明分别保存。

`_facts()` 作为唯一投影入口，按已提交批次与已提交更正生成当前事实；下游不得各自选择原始/最新版本。每个逻辑事实当前最多一个有效版本，作废不会删除原档案。缺失成本、费用、时刻及证据继续显式未知。

## 5. 提交、幂等与恢复

预览必须只读。提交复用 journal 跨 worker 写租约，锁内重读当前批次集合、更正链、目标事实和引用版本，重算同一预览并核对 `preview_digest`、`base_effective_facts_digest` 及预期 head。任何相关变化返回冲突，不把旧页面自动升级成新确认。

更正 ID/请求键由规范化请求稳定确定；服务端时间不进入请求身份和预览摘要。同一请求再次提交返回原回执，后面即使发生撤销也不能重复执行它。内容不同却复用身份须拒绝。

原件、版本分片、前后快照及关联处置先暂存，最终不可变回执是唯一可见开关。缺回执的暂存对象不得进入 `_facts()`、来源当前列表、引用映射或分析；失败重试恢复同一身份。即使暂存与提交不使用多文档事务，也不能出现半套更正生效。提交前检查完整 BSON 预算，超限明确分片或拒绝，不静默截断。

重导原始文件应命中原始请求回执/身份接合，再投影已有更正；**不能把重导的旧值盖回当前版本，也不能复活已作废事实**。当前导入预览会将请求事实覆盖到组合账本，实现更正时必须一并调整。新批次对旧事实提供佐证只追加来源证明，物质差异走独立更正。

批次共享事实按逻辑事实统一更正，并列明全部共享批次。撤回某份来源证明与认定真实成交无效是不同动作；“取消批次”不能直接删除其他批次共享的事实。

## 6. 结构更正、重算与历史读取

费用改动可能保留库存轮 ID，数量、时间、顺序、证券或作废则可能改变起止、拆轮、并轮或删除轮。当前 ID 由账户、证券及首事件生成，不能假定 ID 未变就没有结构变化。

预览对每个受影响账户/证券检查完整关联事件；跨证券/账户变动检查旧、新两侧。收益复用 `build_ledger`，可先全量重算保证正确，不为局部优化另造算法。对比内容至少包括：

- 原/新数量、现金、费用、成本、已实现及清仓收益、资格与未知原因。
- 原/新库存轮完整成员及 `unchanged/changed/split/merged/removed/added` 关系；关系依据明确的逻辑事实/替代对应，不能只按日期或相似价格猜。
- 真实 FIFO 买入成本批、卖出股数与现金切片的前后差异，以及涉及的全部引用。

每次更正冻结精确前后 `ledger_revision`。版本清单必须包含确切批次集合和更正链；仅“第几次更正”不足以排除后来新增的导入批次。历史重建不得混入新批次、当前可变计划、最新定义或最新行情。

原库存轮消失后仍能按 `episode_id + ledger_revision` 读到其成交、来源、FIFO、旧收益、决策、核对、分配及复盘。当前入口可显示已被替代和显式后继链接，不能静默跳转到新轮或直接 404。历史 owner 读取不能再以“库存轮必须属于当前账本”为前提。

## 7. 引用 stale 与显式映射

更正预览逐条列出 owner、对象身份、revision/hash、原账本版本及影响，不只统计“有几个引用”。对受影响引用必须保存 `retain_historical_pending` 或具体 `rebind` 处置；“未受影响”由服务端依赖核验，不能由客户端随意声明。

事实可以在保留历史、待核映射的状态下更正。此时旧引用不丢失、不冒充当前已确认结果，当前页面显示 stale/待核及解决入口，待办按受影响根因生成。映射有独立预览、预期版本、理由和追加事件；一对多、多对一关系显式给出成交子集与股数，不能按比例猜分。

| 引用 | 更正后的规则 |
|---|---|
| 决策 / 冻结计划关联 | 保留原记录、原时间及原证据，用独立关联事件选择新轮与成交子集。当前投影同时展示原所属轮和本次映射；迁移时间不能倒填，也不把事后关联升级成事前证据。 |
| 数量分配 | 有效 fill 身份/版本、数量或 FIFO 变化即待核。先检测 stale，再计算；旧分配可看。用户通过原分配 owner 提交当前轮的完整新分配表，复验真实成本批上限，保存迁移来源。 |
| 过程复盘 | 比较确切事实上下文，旧确认 stale；旧文与旧判断保留，当前确认须用户重新保存，不能自动复制 confirmed。 |
| 预期核对与证据 | 原核对继续属于原决策版本。依赖已更正事实的结论标明待核；独立来源未变化的原观察仍保留，不一概重写结论。 |
| 生产 execution 匹配 | 同时校验生产摘要、有效归档 fill 摘要、存在性及所属关系；任何一侧变化变 stale。通过原匹配 owner 重新预览/确认或解除，不改生产 execution。 |
| 待办处置 | 相关事实变化重开；旧忽略/确认未知不自动搬到新轮。无关根因不反复重开；所有旧理由、事实指纹及实际记录时间保留。 |
| 统计与研究引用 | 真实账户结果每轮一次。未核模式切片退回未分配残余，切片与残余仍对账；冻结报告/实验保留原输入版本，明确已经不是当前账本，重新计算生成新版本。 |

关联事件自身不修改原对象内容 hash，也不替代原 owner 的业务校验。确切原决策可在新轮作为明确映射的引用展示，但不能因此改写作者原意、原证据时间或提高资格。

## 8. 撤销与接口草案

撤销是带 `reverses_correction_id` 的新更正，重新展示当前→拟恢复结果、相关后续更正及引用影响，要求预期当前版本和独立原因。它不删除原更正，也不直接设回旧 head。若期间有其他相关修正，用户须核对明确的补偿结果，不能无条件套用旧反向值。撤销后恢复相同数值也属于新版本，旧忽略、分配或复盘确认不自动复活。

接口沿用 `/api/v1/trade-journal`：

| 方法与路径 | 合约 |
|---|---|
| `GET /batches/{batch_id}` | 原回执、事实/原行、当前有效版本、共享范围和更正历史；大原件按需恢复。 |
| `POST /corrections/preview` | 操作全集、前后差异、账本引用、冲突/未知、受影响引用和映射要求、稳定预览摘要。 |
| `POST /corrections` | 确切预览、预期 head/事实摘要及用户确认；返回不可变回执和待核项。 |
| `GET /corrections`、`GET /corrections/{id}` | 分页审计历史、原件及前后账本/引用处置下钻。 |
| `GET /episodes/{id}?ledger_revision=...` | 确切历史档案；关联 owner 接受同一版本上下文，不能改读当前。 |
| `POST /corrections/{id}/reference-bindings/preview`、`POST /corrections/{id}/reference-bindings` | 显式选择原引用、目标轮/有效事实版本及股数，校验后追加映射。 |
| `POST /corrections/{id}/reverse/preview` | 生成基于当前状态的补偿预览；仍通过正常更正提交入口保存。 |

失效版本/摘要冲突返回 409；格式或业务内容无效返回 422；确切对象不存在返回 404。来源原件恢复继续校验 SHA 与内容 hash。请求不得指定服务器记录时间或伪造已认证身份。

## 9. 必须完成的验收

| 用例 | 可核对结果 |
|---|---|
| 费用/价格修正 | 当前含费收益恰好变化一次；原成交、原件、所有旧回执内容不变；未知费用/成本不自动变零。 |
| 数量/时间/顺序修正 | 构造有效的拆轮、并轮与首事件更换；前后库存、现金、FIFO 正确，旧轮历史仍可读，每条受影响引用有明确处置。 |
| 多行及公司行为 | 相关修正整体可见；股票入账与 IPO 缴款重算成本；分红/税费等仍独立，不重复计现金。 |
| 映射与数量归属 | 不修改旧 decision 所属轮；新分配通过原 owner 验证，不能借后来买入批、超实际 FIFO 股数或自动按比例分摊。 |
| stale 与重核 | 生产 execution 不变而归档 fill 改动时匹配仍 stale；旧复盘不可自动 confirmed；相关待办重开，无关待办稳定。 |
| 共享事实与重复导入 | 共享批次清单完整；取消批次不删除共享事实；重导旧请求仍幂等，不能复活作废事实或覆盖更正版本。 |
| 并发与断点 | 导入/更正并发、两个更正争用、预览后引用变化均校验版本；中途失败的暂存不可见，同请求重试不双计。 |
| 撤销 | 新增反向回执，原链完整；有后续修正时不能直接回退；恢复同数值也保持新版本并重新核对引用。 |
| 原件与历史 | 原件字节及 SHA 可恢复；历史版本排除后续批次/最新配置；旧轮、分配、复盘与原核对可下钻。 |
| 统计 | 当前真实总 PnL 每轮一次；stale 模式切片退回待核残余，切片+残余与账户结果一致，不删失败样本。 |
| API/UI 往返 | 真实领域返回值经预览→确认→重载→历史→映射→撤销完整往返；显示现金、数量、未知、版本与 stale，失效表单不能偷偷换用新预览。 |
| 生产边界 | 前后生产持仓、现金、委托、executions、风险配置与策略定义完全一致；所有业务写入限定 journal 集合。 |
| 备份/隔离恢复 | 新更正、版本清单、暂存/提交状态、映射、来源及索引进入归档；隔离恢复后重放同一账本和引用状态，与 manifest/hash 对账。 |
